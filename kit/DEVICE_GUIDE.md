# 새 장치(조작법) 더하기

**선생님 아이디어는 판에 있는 것에 갇히지 않는다. 판에 없는 것은 무엇이든 새로 만든다.** 판(`platform/`, `src/`)도 고쳐도 된다. 판에 무엇이 있는지 몰라도 된다: 필요한 것이 판에 없다고 여기고 만들면, 운영자가 살펴보고 이미 있는 것과 맞춰 반영한다. 판에 있는 것만으로 되게 하려고 아이디어를 줄이거나 바꾸지 않는다.

보내는 길은 하나다: `npm run submit -- <교과>/<팩>`. 팩 폴더와 고친 판 코드(`platform/`, `src/`, `tests/`, `kit/`)가 함께 도름스로 가고, 운영자가 코드를 살펴본 뒤 저장소에 요청(PR)으로 넣어 싣는다. **GitHub 계정은 필요 없다.** 판 코드가 든 요청은 팩만 보낼 때보다 실리기까지 조금 더 걸린다고 선생님께 말씀드린다.

담는 그릇(작은 것부터. 고르기 어려우면 큰 쪽으로 만든다)
1. 새 물건의 성질(몸, 닿기, 움직임, 놓는 곳)로 된다 → 팩만(`kit/STAGE_FORMAT.md` '새 물건 만들기').
2. 물건 하나가 새 규칙을 가져야 한다(켜고 끄기, 세기, 시간이 지나면 바뀌기, 차례대로 눌러야 열림, 여럿이 동시에 닿아야 켜짐, 넣으면 다른 물건이 되어 나옴, 도름이를 밀어내는 물살 …) → 아래 **새 움직임** 파일 하나. 본보기 `platform/behaviors/grinder.ts`(여럿이 번갈아 눌러 잘게 부수고 다른 물건을 내준다).
3. 조작이나 화면, 규칙 전체가 새로워야 한다(그래프 공장, 줄 묶기처럼 판 전체에 걸친 장치. 도름이끼리 잇기, 크기 바꾸기, 물속 헤엄, 새 조작 …) → 아래 **큰 장치**. 판의 어느 파일이든 고친다.

## 새 움직임 (platform/behaviors/<이름>.ts)

파일 하나에 물건 하나의 규칙을 적는다. 파일 이름이 곧 움직임 이름이고, things.json 의 `"behavior": "<이름>"` 으로 쓴다. 본보기는 `platform/behaviors/toggle.ts`(확인으로 켜고 끄기)와 `timer.ts`(닿으면 켜지고 4초 뒤 꺼짐), 손잡이 설명은 `platform/behavior.ts`.

```ts
import type { Behavior } from '../behavior';

const counter: Behavior = {
  about: '세 번 눌러야 켜진다',
  use: ctx => { ctx.vars[1] += 1; if (ctx.vars[1] >= 3) ctx.vars[0] = 1; return true; },
  useText: ctx => (ctx.vars[0] ? null : `확인: 누르기 ${ctx.vars[1]}/3`),
  frame: ctx => (ctx.vars[0] ? 1 : 0),
};
export default counter;
```

| 손잡이 | 하는 일 |
|---|---|
| `tick(ctx, dt, touching)` | 매 걸음. `touching` 은 지금 이 물건에 닿은(위에 선) 도름이들 |
| `use(ctx, p)` | 가까이에서 확인을 눌렀다. 무언가 했으면 `true` |
| `useText(ctx, p)` | 확인 안내 글(없으면 이름으로 "확인: 등"). `p` 는 안내를 볼 도름이(든 물건에 따라 글을 바꿀 때). 안내 글과 실제로 누를 때 하는 일이 같아야 한다: 안내가 '친구 차례'라면 `use` 도 아무것도 안 하고 `true` 를 돌려준다 |
| `frame(ctx)` | 몇째 그림(frames)을 그릴지 |
| `ctx.vars` | 물건마다 수 4칸. 방 안 모두에게 저절로 맞춰진다. **상태는 여기에만 둔다** |
| `vars[0]` | 0 이 아니면 그 물건 종류의 `opens` 다리가 켜진다 |
| `ctx.respawn(p)`, `ctx.launch(p, 칸)`, `ctx.remove()`, `ctx.isOn(글자)`, `ctx.t`, `ctx.players` | 처음 자리로 보내기, 튕겨 올리기, 물건 없애기, 다리가 켜졌나, 지난 시간, 방 인원 |
| `label(ctx)` | 물건 위에 늘 보이는 글(남은 횟수·단계처럼 바뀌는 이름표) |
| `ctx.place(x, y)` | 이 물건을 옮긴다(판 점). 떠오르는 거품, 밀려 내려가는 음식처럼 장치가 정하는 자리로 |
| `ctx.shove(p, px)` | 도름이를 옆으로 민다(바람, 물살, 꿈틀 운동) |
| `ctx.holding(p)`, `ctx.take(p)`, `ctx.give(p, 이름)` | 든 물건 이름 보기, 든 물건 받아 없애기, `"stock": true` 물건을 손에 쥐여 주기. 넣으면 바뀌어 나오는 장치(음식 → 잘게 부순 음식, 재료 → 부품) |
| `ctx.peek(이름)` | 다른 장치의 수 4칸 읽기(장치끼리 잇기) |
| `ctx.takes`, `ctx.gives` | things.json 의 `takes`(받는 물건 이름들)와 `gives`(내주는 물건 이름). 같은 움직임을 교과마다 다른 물건으로 쓰게 한다. 물건을 든 도름이의 확인은 `takes` 에 그 물건을 적은 장치만 먼저 받는다 |

`useText`, `label`, `frame` 은 화면을 그릴 때 불리므로 읽기만 한다(여기서 `vars` 를 바꾸거나 `give` 를 불러도 아무 일도 없다).
| `p.i` | 도름이 차례. 사람마다 다른 일을 시키는 장치(짝수만 들 수 있는 열쇠 등) |

지킬 것(검사 `tests/behaviors-rules.test.ts` 가 문법 나무로 먼저 거르고, 운영자가 병합할 때 한 줄씩 다시 읽는다. 이 검사 파일과 `platform/behavior.ts` 는 요청이 고칠 수 없다)
- `import type { Behavior } from '../behavior'` 말고는 가져다 쓰지 않는다. 맨 위에는 const, function, export default 만 둔다.
- 바깥과 주고받는 코드(fetch 등), 화면·저장소에 손대는 코드(window, document, localStorage), 시간과 난수(Date, Math.random), `new`, 정규식, `[ ]` 로 속성 고르기(`ctx.vars[0]`~`ctx.vars[3]` 처럼 숫자로 칸을 고르는 것만 된다)를 쓰지 않는다. `ctx` 라는 이름은 움직임 함수의 첫 매개변수로만 쓴다. 같은 입력이면 같은 결과여야 방장이 바뀌어도 이어진다.
- 반복은 `for (let k = 0; k < 10; k++)` 처럼 횟수를 정한다(while, 끝 조건 없는 for 는 판을 멈춘다).
- `use` 가 아무것도 안 했으면 `false` 를 돌려준다(그 누름이 옆의 다른 장치로 간다). 도름이는 사본이라 `vy` 만 바로 바꿀 수 있고, 옮기려면 `ctx.respawn`·`ctx.launch`·`ctx.shove` 를 쓴다.
- 손잡이로 안 되는 일(도름이 크기 바꾸기, 새 조작, 화면 위 창, 도름이끼리 잇기 같은 판 전체 규칙)은 움직임 파일에서 억지로 흉내 내지 말고 아래 **큰 장치**로 판을 고친다. 줄 묶기(`rope`)가 그렇게 판에 들어간 본보기다(`platform/sim.ts` 의 `ropeTick`).
- 다른 교과에서도 쓸 수 있는 이름으로 짓는다(`stomach` 대신 `grinder`). 그림은 팩의 글자 그림으로 갈아 끼우게 둔다.
- 규칙마다 시험을 `tests/` 에 더한다(`tests/things.test.ts` 의 '새 움직임' 시험이 본보기). 혼자서는 안 되게 만들었으면 그것도 시험한다.
- 오류가 나도 판은 멈추지 않고 그 걸음만 건너뛰지만, 그런 일이 없게 직접 해 본다.

보내는 법은 팩과 같다(`npm run submit -- <교과>/<팩>`). 위 약속이 새 움직임에 맞지 않으면 큰 장치로 만든다.

## 큰 장치

수업 내용이 판에 없는 움직임을 요구할 때가 있다(음식을 잘게 부수기, 관을 따라 밀어 보내기, 온도에 따라 녹이기 …). 선생님 아이디어가 그리는 그대로의 장치를 먼저 적는다(무엇이 보이고, 도름이가 무엇을 하고, 그 결과 무엇이 바뀌는지). 그다음 그것을 담을 가장 작은 그릇을 고른다(새 물건 → 새 움직임 → 판 고치기). 있는 장치를 엮어 비슷하게 만드는 것은 흉내다. 흉내로 바꾸려면 선생님께 무엇이 달라지는지 보여 드리고 허락을 받는다. 허락이 없으면 망설이지 말고 판을 고친다. 장치는 코드라서 **운영자가 직접 살펴본 뒤에** 실린다. 팩만 보낼 때보다 오래 걸린다고 선생님께 미리 말씀드린다.

## 먼저 정할 것 (선생님과)

- 무엇이 보이는가, 도름이가 무엇을 할 수 있는가(새 조작이 필요하면 만든다), 그 결과 무엇이 달라지는가.
- 왜 혼자서는 안 되는가. 장치 자체가 여러 사람을 필요로 해야 한다(동시에, 번갈아, 양쪽에서, 여럿이).
- 이 장치를 다른 교과에서도 쓸 수 있는 이름과 모양으로 만든다. `stomach` 가 아니라 `grinder`(여럿이 번갈아 눌러 잘게 부수는 통)처럼. 그림은 팩의 글자 그림으로 갈아 끼우게 한다.

## 어디를 고치나

그래프 공장이 본보기다. 장치가 크면 `platform/<장치>/` 폴더 하나에 모으고, 판(`stage.ts`, `sim.ts`, `render.ts`)에서는 그 폴더를 부르기만 한다. 같은 순서로 따라 한다.

| 파일 | 하는 일 | 그래프 공장에서 볼 곳 |
|---|---|---|
| `platform/graph/legend.ts` | legend 의 새 `type` 읽기와 자리 검사(`stage.ts` 가 부른다). 잘못 적으면 쉬운 한국어로 알려 준다 | `GRAPH_KEYS`, `parseGraphLegend`, `finishGraph` |
| `platform/graph/model.ts` | 장치의 상태와 한 걸음의 규칙(화면과 연결을 모르는 순수 계산). 확인 단추로 하는 일도 여기서 정해 `sim.ts` 의 `actionAt` 이 부른다 | `createGraph`, `graphTick`, `graphActionAt`, `applyOrder` |
| `platform/graph/draw.ts` | 그리기(`render.ts` 가 부른다). 색은 `platform/look.ts` 의 `PALETTE` 와 `platform/sprite.ts` 의 물감만 쓴다 | `drawGrid`, `drawGraphBack`, `drawGraphFront`, `graphHud` |
| `platform/graph/wire.ts`, `platform/graph/order.ts` | 온라인으로 주고받는 값. 남의 기기에서 온 값은 다시 검사한다 | `cleanOrder` |
| `src/graph-panel.ts` | 장치에 딸린 창(찍는 방, 손잡이 방) | `openPanel` |
| `tests/<장치>.test.ts` | 규칙마다 시험. 의도한 풀이로만 깨지는지, 마구 누르는 봇이 못 깨는지도 | `tests/graph-factory.test.ts`, `tests/graph-help.ts`(시험 도우미) |
| `kit/STAGE_FORMAT.md` | 선생님의 AI 가 읽는 설명(놓는 법, 값, 움직임, 자리 약속) | '그래프 공장' 절 |
| `packs/etc/tutorial/` | 그 장치만 써 보는 연습 스테이지 하나 | `02 그래프 찍어 들기` |

## 지킬 것

아이디어를 막는 약속이 아니라, 학생 화면과 여럿이 하는 방이 깨지지 않게 하는 약속이다. 지키기 어려우면 그 까닭을 설계서 '의견'에 적고 만든다. 운영자가 맞춰 반영한다.

- 조작은 되도록 움직이기, 뛰기, 확인 셋 안에서. 새 조작이 꼭 필요하면 만들고 설계서에 적는다.
- 판 밖과 주고받는 코드(fetch, 저장소, 바깥 주소)와 `eval` 류는 넣지 않는다(학생 기기에서 돈다). 새 의존성(`package.json`)은 보내지 못하니, 필요하면 설계서에 적는다.
- 값은 지도와 설정에서 받고, 받은 값은 범위와 모양을 검사한다(남이 쓴 팩이 판을 멈추지 못하게).
- 필요 인원은 숫자보다 `"half"`, `"all"` 처럼 방 인원에 맞춰 풀리는 값으로.
- 화면 글은 쉬운 한국어, 이모지와 긴 줄표 없이. 판정 문구("정답", "오답")를 쓰지 않고, 틀린 까닭이 화면에서 보이게 한다.
- 기존 시험이 모두 통과해야 한다(`npm test`). 기존 장치의 움직임을 바꿔야 하면 바꾸되, 다른 팩이 깨지지 않는지 시험으로 확인하고 설계서에 적는다.

**예외**: 그래프 공장은 운영자 결정(형 지시 2026-11-23)으로 위 약속 두 가지를 넘었다. 식과 숫자를 넣는 창(찍는 방, 손잡이 방)을 열었고, 수식 입력기 MathLive 와 식을 읽는 Compute Engine 을 의존성으로 들였다(그래프 장치가 있는 스테이지에서만 불러오고, 글꼴은 이 사이트에 둔 것만 쓴다). 새 장치도 창이 필요하면 만든다(묻고 멈추지 않는다). 새 의존성은 보내지 못하니, 필요하면 설계서 '의견'에 적어 두면 운영자가 들인다.

## 보내기

판을 고쳤어도 팩과 같은 명령 하나로 보낸다: `npm run submit -- <교과>/<팩>`. 명령이 내려받은 판과 견주어 바뀐 판 파일(`platform/`, `src/`, `tests/`, `kit/` 의 글 파일)을 알아서 모아 팩과 함께 보낸다(`--dry-run` 으로 무엇이 갈지 먼저 볼 수 있다). 그 밖의 파일(`scripts/`, `package.json`, 설정)은 가지 않으니, 그런 바뀜이 필요하면 설계서에 적는다. 설계서의 '의견'에 그 장치가 무엇이고 왜 필요한지 적어 둔다. 운영자가 코드를 살펴보고 화풍과 규칙을 다듬어 싣는다.

GitHub 계정이 있는 선생님은 `npm run submit:code -- <교과>/<팩>` 으로 직접 요청(PR)을 올려도 된다(gh 로그인이 필요하다).
